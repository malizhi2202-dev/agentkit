## ① 头脑风暴（技法：六顶帽）

| 视角 | 产出 |
|---|---|
| 事实 | 单 agent 循环 + 场景/剧本；工具并行执行有步超时；无执行状态持久化（F5） |
| 情绪 | 接入方会觉得"只能做一次问答，做不了长任务" |
| 风险 | 贸然加持久化会破坏"零状态、可整目录搬走"的核心属性 |
| 价值 | 审批点（人在环）与终止策略是**请求内**就能做的，价值/成本比最高 |
| 创造 | 把"编排"降级为"策略配置"，而不是引入图引擎 |
| 流程 | 先用 2 个 change 验证需求，再决定是否上图 |

## ② 竞品与其他产品做法

| 产品 | 做法 | 可借鉴 | 不可取 |
|---|---|---|---|
| [LangGraph](https://github.com/langchain-ai/langgraph) | durable execution（失败后从断点继续）+ HITL interrupts + 记忆 | 审批点是编排的一等公民 | 面向"长时运行平台"，需状态存储 |
| [Eino](https://github.com/cloudwego/eino) | interrupt/resume for HITL + compose 图 | 把 HITL 做成"可暂停的节点" | 图 + 状态一起引入 |
| [tRPC-Agent-Go](https://github.com/trpc-group/trpc-agent-go) | GraphAgent（对标 LangGraph）、Chain/Parallel/Cycle + session/memory 持久化 | 三种组合原语覆盖多数场景 | 需要 session 存储组件 |
| [ADK for Go](https://github.com/google/adk-go) | 多 agent 系统与部署无关 | 组合优于继承 | — |

**关键判断**：竞品的编排能力都建立在"**agent 是长时运行的实体**"这个假设上；agentkit 的假设是"**agent 活在一次请求里**"。两者不是能力差距，是**定位差异**——把长时能力当 KPI 去追，会亲手拆掉自己的护城河。

## ③ 结论与建议

**推荐**
1. **终止策略加强**（候选 6）—— 最小成本换最大安全：最大轮次、重复调用检测、可选预算。
2. **人在环审批点**（候选 4）—— 与治理体系天然契合：`Registry.LookupAuthorized` 之后、工具执行之前加一个可注入 `Approver`；拒绝即 fail-closed。
3. **并行结果合并策略可配**（候选 7）—— 现固定按调用序，接入方可能有"按重要性"需求。

**否决记录**
- 候选 1/3（图引擎 / 断点恢复）：与"无状态请求内"定位直接冲突，且无接入方实证需求（R19 阶梯律：先证明需要，再实现）。
- 候选 10（剧本灰度）：需求不明。

**批判（红队）**：最弱一环是"没有持久化"——但那是**设计选择不是缺陷**；红队唯一有效的攻击是"长任务场景直接出局"，而这类场景本就不是目标用户（写 Go web 程序的接入方）。
