# D-platform-positioning · 框架 vs 平台：定位与边界（六点愿景的前提）

> 审核: **通过**（第 2 轮 · 2026-10-23） · change: `agentkit-evolution` · 依据: `docs/design.md:6-77`（无状态定位）+ 用户六点愿景 + `tools/portability_check.py` 的"可搬走"判据

## ① 头脑风暴（技法：假设反转 + 预演失败）

反转假设："agentkit 就是一个库。"——反转后：如果它要承载注册中心、控制台、扫描器、长驻壳，它就不再是库，而是**平台**。而平台与库的工程要求完全不同（进程模型、配置、升级、多租户）。

三种形态：

| 形态 | 描述 | 好处 | 代价 |
|---|---|---|---|
| A 纯框架 | 现状，零宿主依赖、请求内无状态、可整目录搬走 | 护城河：可嵌入任何 Go 服务 | 无法承载点 4/5/6 的长驻能力 |
| B 框架 + 独立能力运行时 | 核心仍可搬走；新增 `agentkit serve`（单二进制）承载导出/扫描/注册 | 既保留护城河又满足 6 点 | 多一个产物要解释 |
| C 一体化平台 | 单仓库单进程，UI+注册+扫描+运行时全内置 | 演示效果好 | 依赖膨胀、部署重、护城河消失 |

| # | 候选 | 影响 | 可行性 |
|---|---|---|---|
| 1 | 保持 A（只做框架，其它不做） | 低 | 高 |
| 2 | 选 B：核心零依赖 + `agentkit serve` 侧车 | 高 | 高 |
| 3 | 选 C：一体化平台 | 中 | 低 |
| 4 | 拆仓：核心仓 + ext 仓（对齐 Eino 的 eino-ext 模式） | 高 | 中 |
| 5 | 单二进制但内部分层（cmd + internal） | 高 | 高 |
| 6 | 协议优先：核心只定义 Capability，导出全部走插件 | 高 | 中 |

## ② 竞品与其他产品做法

| 产品 | 做法 | 可借鉴 |
|---|---|---|
| [Eino](https://github.com/cloudwego/eino) | 核心仓 + **eino-ext**（组件/回调/工具）+ examples 仓分离 | 核心轻、生态重，扩展不污染依赖 |
| [tRPC-Agent-Go](https://github.com/trpc-group/trpc-agent-go) | 单仓全功能（agent/runner/server/telemetry） | 一体化可行但依赖面大 |
| [OpenHands](https://github.com/OpenHands/OpenHands) | 多仓分工：Canvas / SDK / automation / client | 壳与内核分离 |
| [MCP Registry](https://github.com/modelcontextprotocol/registry) | 独立服务，不自带 agent 运行时 | 注册与执行解耦 |

**关键判断**：三个成熟项目都是**核心轻、外围重**（ext/多仓/解耦服务）。没有一个是"单仓把 UI、注册、执行、扫描全塞进去"。

## ③ 结论与建议

**推荐 B（候选 2+5）**
1. **核心 18 包保持零宿主依赖、请求内无状态、可整目录搬走**（护城河不动）。
2. 新增 **`agentkit serve`**：单二进制承载 MCP/A2A 导出、注册中心对接、能力编目、扫描器；内部按包分层，外部只见一个进程。
3. 控制台 UI **不自研**，复用 OpenHands 类壳（见 `D-agent-shell.md`）。

**否决**：候选 3（一体化平台，护城河消失）；候选 4（拆仓，当前规模不值得，等 ext 代码量过阈值再拆）。

**批判（红队）**：B 的最大风险是"**两个产物**"——接入方要理解"什么时候用库、什么时候起服务"。缓解：`agentkit serve` 从同一个 `Capability` 编目生成，库模式是"进程内导出"，服务模式是"跨进程导出"，**同一套配置、同一套授权**。
