## ② 竞品与其他产品做法

| 产品 | 做法 | 可借鉴 | 不可取 |
|---|---|---|---|
| [openapi-mcp-server](https://github.com/snaggle-ai/openapi-mcp-server) | 解析 OpenAPI 规格，让 agent 检索/理解接口 | **规格即能力清单**，成本最低 | 只做"读"，不做"生成能力" |
| OpenAPI 生态（转换器类项目，类别级，未逐一抓取来源） | 把 OpenAPI operation 映射为 MCP tool | 输入 schema 可直接复用 | 质量参差，生成的工具描述不适合 LLM 选 |
| [MCP Registry](https://github.com/modelcontextprotocol/registry) | 发布需命名空间所有权验证 | 能力清单要能被验证来源 | — |
| 传统 API 网关（Kong/Apigee 等） | 从流量/规格生成 API 目录 | 被动发现是成熟做法 | 依赖部署环境 |

**关键判断**：老服务**大概率已经有 OpenAPI 或至少能导出路由表**。从规格出发的成本，比从流量或代码出发低一个数量级。

## ③ 结论与建议

**推荐**
1. **OpenAPI 优先**（候选 1）→ **代码扫描其次**（候选 2 的 Go AST 子集）→ **手工 YAML 兜底**（候选 4）。
2. **扫描只出提案**（候选 5+6）：分类建议带置信度，**人工确认后才进入编目**——这是治理不被破坏的前提。
3. **生成可编译骨架**（候选 7）：让接入方在 10 分钟内跑通一个能力，而不是抄文档。

**否决**：候选 3（流量被动发现，依赖环境且隐私敏感）；候选 9（调用量反查，需要额外埋点）。

**批判（第一性原理）**：这件事的价值不在"扫描"这个动作，而在**把"老服务的隐式接口"变成"显式的、可分类、可授权的能力条目"**。扫描只是入口，确认与分类才是产物。
