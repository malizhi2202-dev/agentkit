## ① 头脑风暴（技法：类比迁移 + 逆向）

逆向："怎么让这套导出面变成新的安全漏洞？"——答：**导出时不分类、不授权、不审计**，等于给外部开了一扇绕过 D1-D4 的后门。这恰好是最容易犯的错。

## ② 竞品与其他产品做法

| 产品 | 做法 | 可借鉴 | 不可取 |
|---|---|---|---|
| [tRPC-Agent-Go](https://github.com/trpc-group/trpc-agent-go) | MCP 工具 + A2A + AG-UI **一站式** | 三协议同源导出是可行的 | 绑定其生态 |
| [MCP Registry](https://github.com/modelcontextprotocol/registry) | Go 实现，API v0.1 已冻结；`mcp-publisher` CLI 发布；命名空间需 GitHub/DNS 验证 | **直接对接，别自建** | 自建一套注册中心 |
| [A2A](https://github.com/a2aproject/A2A) | JSON-RPC 2.0 + AgentCard 发现 + SSE；**有官方 Go SDK**；Linux Foundation | AgentCard 即能力名片 | 需要独立进程承载 |
| [OpenHands](https://github.com/OpenHands/OpenHands) | Agent Server REST + 多后端（含 ACP） | 壳与能力分离的架构先例 | 绑定其 Python 栈 |

**关键判断**：注册中心**已经有事实标准**（MCP Registry），自建等于重复造轮子且没人发现得了你的服务器；导出面的真正难点不是协议，而是**"导出的能力是否仍受治理"**。

## ③ 结论与建议

**推荐**
1. **MCP 服务端导出**（候选 1）+ **A2A AgentCard**（候选 2），两者共享候选 9 的投影层。
2. **对接 MCP Registry**（候选 3），不自建（否决候选 4）。
3. **导出必须过治理**（候选 5+6+7）：导出面 ⊆ 入域能力；出域能力禁止导出；每次调用落审计。

**否决**：候选 4（自建注册中心，与标准脱节）；候选 10（AG-UI 暂不需要）。

**批判（红队）**：最弱一环是"导出即提权"——D3 中立能力一旦被导出，外部就能用它做双向动作。防御点：**导出面单独一张白名单**，与内部 Registry 的授权表分离，且默认空。
